# tap: Design and implementation review

Oct 20, 2026 · `main` at `fc7ee0f`

This review covers the whole repository. It looks for gaps in design and implementation: where the code falls short of the [design goals](Agent-as-OCI%20+%20Harness%20Design.md), where the code and the docs disagree, and what to do next.

Some gaps are already accepted in the plans' "Known gaps" lists: DNS exfiltration, CONNECT-only egress, admission in audit mode, `effectsPolicy: ask`, and the rest. They are not repeated here, unless the code is worse than documented or the reason for accepting them no longer holds.

**Method.** There were six reviews, one per subsystem:

- runtime: harness, runner and MCP;
- egress and hooks;
- console;
- spec, bundle, render and admission;
- factory;
- deploy, CI and operations.

Every finding was traced to the code, and several were confirmed with throwaway tests that aren't committed. Every High finding was re-checked by hand against the source. Items marked *(unconfirmed)* were read in the code but not reproduced, usually because they depend on how the cluster or the gateway behaves. Nothing was run against the cluster, OpenBao, the registry or GitHub.

**Test suite at this commit.** `go vet ./...` is clean, and `go test -race ./...` passes in every package (CI doesn't run the race detector yet). The factory's typecheck and its 30 tests pass. Coverage:

| Package | Coverage |
| --- | --- |
| `pkg/*` | 60–89% |
| `cmd/console` | 74% |
| `casa-collector` | 61% |
| `cmd/tapctl` | 23% |
| `cmd/harness`, `cmd/runner`, `cmd/hooks`, `cmd/egress-proxy`, `cmd/factory-publisher` | 0% |

## Summary

The core architecture holds up. These choices are sound:

- agents as data on two curated images;
- a uid per tool, and whole-slot argv substitution;
- per-call egress credentials, checked against the IP actually dialed;
- reproducible bundles, and two signing keys in OpenBao Transit;
- CI that stores no credentials, and Flux applying only signed artifacts.

Most of the implementation is careful too: constant-time comparisons, size caps, strict decoding, `html/template`, and secrets passed on stdin.

The gaps cluster in three places.

1. **Identity is asserted, not verified.** The console, the harness's chat port and the factory API all read the caller's identity from a header without checking it, and rely on network position to keep impostors out. That position is weaker than assumed. The console has no NetworkPolicy. The harness and the factory share a loopback interface with code they don't trust: tools, and the model's shell. In each case one `curl` can impersonate any user.
2. **A signature doesn't contain what it signs.** Several controls assume a signature bounds what can happen, but the boundaries behind the signatures leak:
   - the "narrow" Flux appliers can create Deployments that run as cluster-admin service accounts;
   - CI signs whatever image is already at a tag;
   - the bundle build follows symlinks out of the agent directory;
   - a secret *name* like `NODE_OPTIONS` turns a write-only secret value into unreviewed code.

   The permission diff, which the planned auto-merge will rely on, misses several widenings.
3. **Single, stateful choke points with no recovery plan.** tap-hooks, the egress proxy and the console are single replicas with state held in memory. Unauthenticated requests can hold the only public endpoint at 503. zot and the console's ConfigMaps have no backup, and nothing alerts on any of it.

Separately, in the agent pod and in the factory, untrusted processes can outlive the call that started them. That undermines the isolation of both. In the runner it also wedges the process while its health check stays green.

## 1. Identity (ID)

Three services read the caller from a header without checking it, on the grounds that "only the gateway can reach us". That assumption fails differently for each one.

### ID-1 · High · The console trusts an unverified identity header, and any pod can reach it

- **Where:**
  - `cmd/console/main.go:244-258`;
  - `deploy/platform/apps/console.yaml`. The console has no NetworkPolicy, and `tap-system` has no default-deny; only egress-proxy and tap-hooks have policies.
- **What happens:** `user()` base64-decodes the JWT payload of `x-tap-identity` and returns `email`. It never checks the signature, `iss`, `aud` or `exp`. Any pod in the cluster can call `tap-console.tap-system:80` with a hand-made token and act as any team member. It can then:
  - write any agent's secrets to OpenBao;
  - create hooks (the response carries the new credential), and trigger the agent through the public hooks URL;
  - read every run trace;
  - open agent.yaml PRs through the publisher.

  The factory's `/console/*` routes trust the console's team check, so the forgery carries through to them.
- **Fix:**
  - Add a default-deny NetworkPolicy in `tap-system`, and admit the console only from the `tap` Gateway's Envoy pods, as agent namespaces already do.
  - Verify the token against Dex's JWKS (issuer, `aud: tap`, `exp`). One small package shared by the console and the harness keeps the two consistent.
  - Check that Envoy *replaces* a client-supplied `x-tap-identity` instead of adding a second one, since `Header.Get` returns the first value *(unconfirmed)*.

### ID-2 · High · Tools can drive the harness's chat port as any user

- **Where:** `pkg/harness/server.go:26-30` and `320-345`; `pkg/render/templates/agent.yaml.tmpl:453` (`--listen=:8080`).
- **What happens:** the harness decodes `x-tap-identity` the same way, and justifies it by the NetworkPolicy. But NetworkPolicy doesn't filter loopback, and tool processes share the pod's network namespace. The trigger port has a token for exactly this reason (`server.go:44-47`); the chat port doesn't. Tool A can:
  - `POST 127.0.0.1:8080/v1/chat` as anyone, or as `hook:<name>`;
  - ask the model to call tool B, and read B's results over SSE;
  - spend the shared model key.

  The second point is a confused deputy: it crosses the per-tool uid and secrets boundary. Separately, a missing header falls back to a shared `anonymous` user instead of a 401.
- **Fix:**
  - Verify the token with ID-1's package.
  - Refuse callers on `:8080` that come from loopback or the pod's own IP.
  - Return 401 when there is no identity.
  - Reserve the `hook:` prefix.

### ID-3 · High · The model's shell can call the factory API as anyone

- **Where:** `factory/src/api.ts:196-198`; `factory/src/main.ts:93-95`; `deploy/factory/apps/factory.yaml:69` (`FACTORY_LISTEN 0.0.0.0:8080`).
- **What happens:** the only check is that `x-tap-user` is non-empty, and the NetworkPolicy that admits only the console doesn't apply on loopback. A prompt-injected model (from a spec, or any page it fetches over `*:443`) can run `curl --noproxy '*' 127.0.0.1:8080/…` to:
  - open `/console/agents/<any>/pr` egress-widening PRs "requested by" anyone, skipping the console's team check;
  - read every job's spec, brief and report;
  - start, abort or answer jobs.

  This contradicts the plan's statement that the sandbox can't read job records.
- **Fix:** a console→factory bearer token, mounted 0440 root like the publisher's so uid 61000 can't read it, and a separate token for `/console/*`.

## 2. Supply chain and policy (SC)

### SC-1 · High · The Flux appliers can escalate through Deployments

- **Where:** `deploy/flux/agents.yaml:49-83`; `deploy/flux/platform.yaml:55-112`; `deploy/flux/flux.yaml:3926-3940`.
- **What happens:** `tap-agents-applier` is a ClusterRole that can create namespaces, service accounts, ConfigMaps and Deployments in *every* namespace. A Deployment can run as any service account in its namespace, and `kustomize-controller` in `flux-system` is bound to `cluster-admin`. So a signed agents artifact containing a Deployment in `flux-system` gets cluster-admin. The applier limits nothing beyond what the artifact's signer already controls.

  The platform applier is similar. It can run a pod as `tap-platform-secrets`, which writes `tap-platform/*` in OpenBao: the model key, the trigger token and the sessions key that every agent reads. It can also mount any Secret in `tap-system`. The docs say the appliers manage "only the kinds `tapctl render` emits". That's true of the kinds, but it misdescribes what they can do with them.
- **Fix:**
  - Add a ValidatingAdmissionPolicy keyed on each applier's username:
    - namespaces only with the agent label and prefix;
    - `egress-policy-*` ConfigMaps only in `tap-system`;
    - `serviceAccountName` only `agent` or `tap-secrets`;
    - no deletes outside agent namespaces.
  - Run kustomize-controller with `--default-service-account` and `--no-cross-namespace-refs`.

### SC-2 · High · CI signs whatever image is already at a tag

- **Where:**
  - `ci/build-image.sh:14-27` and `ci/lib.sh:61-66`;
  - `deploy/platform/infra/zot.yaml`: user `tap` has create and update on every `tap/*` repository;
  - `Taskfile.yml` `images:push`.
- **What happens:** if the content-hash tag already exists, CI skips the build and signs the digest it finds with `tap-build`. Tags are predictable, because they are a hash of files in the PR. Three identities can push them:
  - CI;
  - `tap-platform-ci`;
  - the operator's `tap` user, whose password is `.tap/registry.pass`. The docs say nothing in `.tap/` matters.

  Push a modified image under the tag of a pending PR, and CI signs it and Flux applies it. `task images:push` still pushes the apps images under the same tags, so the laptop is a second build origin for "CI-built" images.
- **Fix:** sign only what the job built, and fail when the tag exists without a signature. Remove the `tap` user's create and update rights on the apps repositories, and stop `images:push` from pushing them.

### SC-3 · High · The bundle build follows a symlinked `agent.yaml` or prompt out of the agent directory

- **Where:** `pkg/bundle/bundle.go:57-59` and `139`; `pkg/spec/validate.go:71-82`.
- **What happens:** `walk()` refuses symlinks, but `agent.yaml` and the prompt are added directly and read with `os.ReadFile`, which follows them. Validation only checks the path string, so a PR with `system.md -> ~/.kube/config` validates cleanly. Then `task agent:preview`, run on the operator's machine:
  1. builds the unreviewed PR branch;
  2. pushes the bundle to a registry with anonymous reads;
  3. serves the file as the preview's system prompt, which any Dex user can ask the agent to repeat.

  CI builds are exposed the same way.
- **Fix:**
  - `Lstat` every source and refuse anything that isn't a regular file. Better, read the whole bundle through `os.Root`.
  - Apply the same check in `validator.exists`.
  - Apply it in the harness's `read_skill_file` (`pkg/harness/agent.go:118-132`), which also follows symlinks at runtime.

### SC-4 · High · Secret names become environment variables, with no denylist

- **Where:** `schema/agent.v1.json:103` (`^[A-Z][A-Z0-9_]{1,63}$`); `pkg/runner/runner.go:317-328`.
- **What happens:** the runner appends `NAME=value` for each declared secret after its own variables, and the last duplicate wins. A secret named `NODE_OPTIONS`, `PYTHONPATH`, `PYTHONSTARTUP` or `LD_PRELOAD` validates. Its value is set write-only through the console and can never be read back, yet it becomes code (for example `NODE_OPTIONS=--import=data:…`). That code is not in the bundle, its digest, its review, its attestation or its signatures. Names like `PATH`, `HOME` or `TAP_*` silently break tools instead.
- **Fix:**
  - Reject reserved names in validation, and again in the runner: `NODE_*`, `PYTHON*`, `LD_*`, `PATH`, `HOME`, `TMPDIR`, `LANG`, `LC_*`, `TAP_*`, `*_PROXY`, `SSL_*`, `BASH_ENV` and similar.
  - Longer term, deliver secrets as files or under a fixed prefix.

### SC-5 · Medium · The permission diff misses widenings

- **Where:** `pkg/spec/diff.go:47-75` and `137-140`; `cmd/tapctl/main.go:164-169` and `190-194`.
- **What happens:** the diff compares tool and secret *names*, egress, MCP servers, effects and the runner. It doesn't see:
  - a secret's `from` changing (`readonly-token` → `admin-token`);
  - `metadata.owner` changing, which moves console authority and run history;
  - the model route;
  - exec argv, a loosened `input_schema`, or timeouts;
  - MCP `auth`, or pinned schemas;
  - tool code, the prompt, or skills.

  The exit codes have problems too:
  - a runner change counts as non-widening;
  - "version not bumped" (exit 1) is returned before "widens" (exit 3), and masks it;
  - a base ref that fails to resolve (a shallow clone, a typo) silently becomes "new agent", and the attestation records base `none`.
- **Why it matters now:** gitops phase 6 plans to auto-merge PRs whose diff exits 0.
- **Fix:**
  - Treat changes to `from`, owner, model and MCP auth as widening.
  - Report changes to exec, schema, timeouts and resources.
  - Hash the content outside `agent.yaml`, and give "code changed" its own exit code.
  - Fail when the base can't be resolved.
  - Let a widening take precedence over the version check.

### Accepted gaps whose premises changed

- **Namespace creation:**
  - The implementation plan (phase 8) accepts that `tap-secrets` can log in from any namespace, because "creating namespaces already needs cluster admin".
  - bundles-and-signing.md relies on the same premise for previews: "Creating these namespaces takes cluster admin".
  - Neither holds: `tap-agents-applier` can create namespaces and service accounts cluster-wide (SC-1).
  - Also, `tap-factory` receives the three shared platform secrets through this role without needing them.
  - Fix: bind the role to `agent-*` namespaces, and give the factory its own role.
- **"All jobs share the sandbox uid … jobs run one at a time"** (phase 9). Processes started by one job survive into the next (FA-1), so "one at a time" doesn't hold.
- **"Nothing in `.tap/` is a credential that can't be regenerated"** (README, architecture.md):
  - The registry push password is enough to get an image signed (SC-2).
  - `registry:creds --force` also regenerates the CI passwords that are stored in OpenBao (OP-3).

## 3. Agent runtime: harness and runner (RT)

### RT-1 · High · Escaped tool processes wedge the runner and survive the kill

- **Where:** `pkg/runner/runner.go:359-389` and `420-424`; `pkg/runner/server.go:33-38`.
- **What happens:** each tool runs in its own process group, and a timeout kills the group and then waits. But `exec.Cmd` has no `WaitDelay`, and `Wait` blocks until stdout and stderr reach EOF. A child that calls `setsid` leaves the group, survives the kill and keeps the pipes open. Examples are Node's `spawn({detached: true, stdio: 'inherit'})` and libraries that daemonize. Then:
  - the call's goroutine and its concurrency slot leak;
  - after four such calls (`--concurrency`) the runner serves nothing, while `/healthz` still returns 200, so nothing restarts it;
  - escaped processes keep running under the tool's uid across calls.

  A background child in the same group also turns a successful call into a timeout.

  Orphans are re-parented to `tap-runner`, which is PID 1 and never reaps them, so zombies pile up. `TestTimeoutKillsProcessGroup` can't see this: it uses `kill(pid, 0)`, which succeeds on a zombie.
- **Fix:**
  - Set `cmd.WaitDelay`.
  - After every call, kill every process of that tool's uid: a helper that calls `setuid` and then `kill(-1, SIGKILL)`, or one cgroup per call.
  - Make `/healthz` report saturated slots.
  - Run an init (tini or catatonit) as PID 1.

## 4. Hooks and egress (EG)

### EG-1 · High · Unauthenticated requests can hold tap-hooks at 503

- **Where:** `pkg/hooks/store.go:202-219`; `pkg/hooks/receiver.go:79`.
- **What happens:** before the receiver knows whether a hook exists, `Lookup` may reload settings, and it does so with the *request's* context. On any error, including `context canceled`, it clears the snapshot and answers "hook settings are unavailable" for the next two seconds. A `POST /h/aa/bb` that disconnects mid-reload is enough. Sending one every couple of seconds keeps every hook down, and GitHub doesn't retry failed deliveries. Reproduced with a throwaway test. It's *unconfirmed* whether Cloudflare, NPM and the Tailscale proxy pass the client's abort through quickly enough.
- **Fix:**
  - Load with `context.WithoutCancel` plus its own timeout, under singleflight.
  - Don't treat cancellation as a failure.
  - Keep the last snapshot through transient errors, and drop entries only when they are explicitly removed.

## 5. Factory (FA)

### FA-1 · High · Model-spawned processes outlive the command and the job

- **Where:** `factory/src/tools.ts:52-62`; `factory/src/gates.ts:19-48`; pi-durable's `NodeExecutionEnv`, which settles after the child exits and kills nothing else.
- **What happens:** `nohup … &` survives every call, `setsid … &` survives timeouts and aborts, and nothing ever kills uid 61000's processes. All jobs share that uid, so a process left behind by job A can:
  - find later jobs through `/proc/*/cwd`;
  - edit their checkouts between the gates and `agentFiles()`, so the PR carries files that were never validated, under a body that shows the old permission diff;
  - read later jobs' egress tokens from `/proc/<pid>/environ`.

  This turns the documented gap "jobs share the sandbox uid … jobs run one at a time" into a live one.
- **Fix:**
  - Kill every uid 61000 process (`setpriv --reuid=61000 … kill -KILL -1`) after each command, at the end of each turn, and before the gates.
  - Run the gates on a root-owned copy, and publish exactly the bytes that were validated.
  - Give each job its own uid.

### FA-2 · High · One large file crash-loops the factory

- **Where:** `factory/src/gates.ts:53-69` and `87-101`; `factory/src/jobs.ts:162-168` and `313`.
- **What happens:** the scope gate reads every file in the checkout whole, as root. A 1.5 GB sparse file (made with `truncate -s`) exceeds the 2Gi memory limit. On restart, `resume()` re-runs the gates for the same job with no attempt counter, and the job timer starts again. The result is CrashLoopBackOff for everyone.
- **Fix:** hash files as streams with a size cap, failing scope above a few MiB. Count attempts per job, and fail the job after N.

## 8. Design gaps

These need a decision rather than a patch.

- **Authentication between services.** Every internal hop authenticates differently:
  - a header: the console, the harness's chat port, the factory API;
  - a shared token: the trigger, the runner, the publisher;
  - an HMAC: egress;
  - nothing at all: tools calling the harness on loopback.

  One rule would close ID-1 to ID-3 and most of what FA-1 can reach: *every listener verifies its caller cryptographically, and nothing trusts loopback in a pod that runs untrusted code.* Two pieces cover it: a shared package that verifies Dex tokens, and a separate token for each internal caller, mounted where tools and the sandbox can't read it.
- **Who may use an agent.** Every Dex user can chat with any agent (ID-4), while hooks and run history are limited to the owning team. And with `effectsPolicy: ask` unimplemented, a write-capable agent is either `auto` for anyone signed in, or `deny`. Per-agent access and approvals (roadmap phase 10) belong together.
- **Turns that outlive a connection.** Three gaps have the same fix:
  - chat turns end when the SSE connection does (RT-7);
  - hook runs die with the pod (RT-6);
  - tap-hooks never retries (EG-15).

  The fix is a small durable turn model: accept, queue, run, and an event log that can be resumed by session. It also answers the design doc's open question about long tasks, and lets the harness and tap-hooks scale past one replica.
- **Shared platform credentials.** The model key, the trigger token and the sessions write key are the same in every agent namespace, so one leak affects every agent. Per-agent model keys are parked. The trigger token and the sessions key could go per-agent with the same PushSecret pattern as egress keys.
- **State outside git.** Hooks, titles and hook credentials live only in a ConfigMap and a Secret, with no history and no backup (OP-1). Either treat them as config, edited by PR to tap-agents like egress, or as data with a backup.
- **What the digest covers.** The design promises that what runs is exactly what was reviewed. Today these inputs escape that:
  - secret values that act as code (SC-4);
  - files the bundle picks up outside review (SC-3, SC-8);
  - changes the diff doesn't see (SC-5).

  It's worth one pass that lists every input to a running agent and checks that each is in the digest, in the diff, or explicitly out of scope.
- **Admission is still advisory.** Enforce mode is blocked on the Kyverno stall, so many controls only report:
  - rule 6;
  - the registry and digest checks;
  - tested signatures;
  - previews.

  Enforce mode plus the applier policy from SC-1 is what bounds "write access to main is deploy access". Timebox the stall investigation; routing Kyverno to zot without going through the gateway is cheap to try.
- **Observability.** The logs are structured, but there are no metrics: tool latency, model errors, egress denials, hook outcomes, queue depth. With one operator, alerts on a handful of signals matter more than dashboards.

## 9. Testing and CI

CI runs gofmt, `go vet`, `go test`, and the factory's typecheck and tests. The gaps, roughly in order of value:

- **Add `-race`** to `go test`. It already passes at this commit, so it costs nothing.
- **Validate manifests on PRs.** Run `deploy/apps.sh render` and `kustomize build` of the infra, apps, factory, flux and ci directories, and pass those and `tapctl render`'s output through kubeconform. Today a broken render is only found after merge, and SC-11's invalid labels pass every test.
- **Static analysis and dependencies.**
  - staticcheck or golangci-lint;
  - govulncheck;
  - shellcheck (the scripts already carry shellcheck directives);
  - Renovate for action SHAs, Go and npm modules, base images, Helm charts and Flux.

  `npm audit` is disabled, with nothing in its place.
- **Docker builds on PRs** (build only), and an image scan.
- **The isolation suite is manual,** and it misses the paths found here:
  - tools calling the harness on loopback (ID-2);
  - tampering with `/workspace/sessions` (RT-2);
  - writing to `$HOME` (RT-3);
  - processes that survive a call (RT-1);
  - DNS exfiltration;
  - CONNECT to OpenBao (`192.168.2.131:8443`) and the API server (`192.168.2.221:6443`), which the proxy's own NetworkPolicy allows.

  A nightly run would catch regressions.
- **Fixtures don't run in the production privilege model.** The test Job has no per-tool uids, no capabilities and no secrets directory. Uid separation, `HOME` permissions and secret file modes are therefore never exercised, which is why RT-3 is invisible to it.
- **The factory sandbox has no automated test in its image** covering these:
  - commands run as 61000;
  - secrets are unreadable;
  - loopback is refused;
  - background processes are killed.
- **Untested entrypoints.** `cmd/harness`, `cmd/runner`, `cmd/hooks`, `cmd/egress-proxy` and `cmd/factory-publisher` have no tests for flag wiring or shutdown. `cmd/tapctl` is at 23%.
- **Specific unit tests worth adding:**
  - `Cache.Lookup` with a cancelled context;
  - range over an integer literal;
  - `splice` with a stalled peer;
  - `public()` for 100.64/10, fc00::/7 and NAT64;
  - `user()` with malformed or unsigned tokens;
  - diff exit-code precedence, and bases that can't be resolved;
  - a symlinked prompt;
  - reserved secret names;
  - preview label values;
  - SigV4 for a GET with a query string.

## Suggested order

**First: a few hours each; closes the High findings with the widest reach.**

1. A default-deny NetworkPolicy in `tap-system`, with console ingress only from Envoy. Verify Dex tokens in a package shared by the console and the harness (ID-1, ID-2).
2. Refuse loopback and own-pod callers on the harness chat port. Add a console→factory token that the sandbox can't read (ID-2, ID-3).
3. tap-hooks (EG-1 to EG-3):
   - detach the settings load from the request, and keep the last snapshot;
   - refuse range over integers;
   - bound concurrent body reads.
4. `Lstat` bundle sources. Reserve secret names in validation and in the runner (SC-3, SC-4).
5. CI signs only what it built. Drop the operator's push rights on the apps repositories (SC-2).
6. Runner and factory processes (RT-1, RT-3, FA-1):
   - in the runner: `WaitDelay`, kill the tool uid's processes after each call, an init as PID 1, and fixed `.home` permissions;
   - in the factory: kill uid 61000's processes after each command.
7. Factory: streamed, capped hashing, and an attempt counter (FA-2).

**Next: before enforcing admission and turning on auto-merge.**

- An admission policy that constrains the Flux appliers, and kustomize-controller's `--default-service-account` (SC-1).
- Spec and policy:
  - permission diff coverage and exit codes (SC-5);
  - rule 2, and rule 4 for MCP URLs (SC-6, SC-7);
  - reserved names and label validation (SC-9, SC-11);
  - the preview label (SC-10).
- Backups for zot and the console's state, and a minimal set of alerts (OP-1, OP-2).
- Egress proxy caps, serving the last good policy, and two replicas (EG-4 to EG-6, OP-4).
- CI: `-race`, manifest validation, govulncheck, shellcheck, Renovate, and base images pinned by digest (SC-13, section 9).
- Fix the docs listed in section 10.

**Then: design work.**

- Per-agent access and approvals, together (ID-4, roadmap phase 10).
- Durable turns and a hook queue (RT-6, RT-7, EG-15).
- Per-agent trigger and sessions credentials; sessions off the workspace (RT-2, RT-13, EG-14).
