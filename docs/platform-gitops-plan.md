# tap: platform GitOps plan

Merging a change to a platform service should be enough to deploy it, as it already is for agents ([gitops-plan.md](gitops-plan.md)). Today someone runs `task images:push`, commits the new digests and runs `kubectl apply` by hand. Nothing ties the code that's running to the config it reads. On Oct 16 `task console:config` published a `platform.yaml` with `secrets.egressPrefix`, but the console running on the cluster was built before that field existed. It couldn't parse the file, so every agent's settings went read-only (#51, #52).

This plan builds the platform images in GitHub Actions and lets Flux apply them, together with `platform.yaml`, from one signed artifact per commit.

## Goals and non-goals

- **Merge = deploy** for the services that change often: console, hooks, egress-proxy, factory and factory-publisher.
- **Code and config ship together.** The `tap-platform` ConfigMap and the images that read it come from the same commit and the same artifact.
- **A bad config doesn't replace a good pod.** If a new build can't start with its config, the rollout stalls and the old pod keeps serving.
- **Revert = rollback**, as for agents.
- Not in scope: the infrastructure the services sit on. That's the gateway, certificate, zot, Dex, OpenBao objects, RBAC and the Secrets the console writes, and they keep `task platform:up` (see Decisions). Runner, harness and casa-collector images also stay out. They're pinned in `platform.yaml` and reach agents through tap releases (`tap.version`), which is a separate contract.

## Decisions (proposed)

| Topic | Proposal | Why |
| --- | --- | --- |
| What Flux owns | An **apps** layer: the services' Deployments, Services, NetworkPolicies and the `tap-platform` ConfigMap. The **infra** layer (Namespaces, RBAC, ServiceAccounts, HTTPRoutes, Gateway, Certificate, zot, PVCs, ESO objects, Secrets) stays with `task platform:up` and `task factory:deploy`. | Infra changes a few times a month, and applying it needs near-cluster-admin rights: whoever can create ClusterRoleBindings can grant themselves anything. The apps layer needs only namespaced Deployments, Services, ConfigMaps and NetworkPolicies, so its applier can be narrower than `tap-agents-applier`. zot also serves registry.hiddenfield.dev through the gateway, and Flux pulls the artifact from it. If Flux managed zot or the gateway, a bad rollout could cut off the source needed to fix it. |
| Trigger | Every push to `main` of this repo, after `ci.yml`'s checks pass | Same as agents. There's one cluster, so tags would only add a manual step back. |
| Digests | No digests in git. CI writes them into the artifact's `kustomization.yaml` (`kustomize edit set image`) | Without this, CI has to commit pins back to `main`, which means bot commits, CI loops and fights with branch protection. The artifact (`tap/platform-manifests:<sha>`) is the pinned record, and git history is still the source of truth. |
| What CI rebuilds | Each image is tagged with a hash of its inputs' contents (`git ls-tree -r HEAD -- <inputs> \| git hash-object --stdin`). If zot already has that tag, the image isn't rebuilt. | A docs-only merge shouldn't restart every service. Docker builds aren't byte-reproducible, so we can't use the digest for change detection as we do for agents. A content hash gives the same effect, and a revert finds the exact image that ran before. |
| Config rollout | `tap-platform` is generated by `configMapGenerator` from `platform.yaml`, with the hash suffix kept | A `platform.yaml` change renames the ConfigMap, which rolls the Deployments that mount it. A console that can't load it exits at startup (`main.go`), so the new pod never becomes ready, the old one keeps serving and Flux's `wait` fails. #52's reload fallback stays as a second safety net. `task console:config` goes away. |
| Signing | The existing `tap-build` key (Transit `tap-signer`), through a new OpenBao JWT role `tap-platform-ci` bound to `ipedrazas/tap`, `refs/heads/main` and the platform workflow | `tap-build-pub` already sits in `flux-system`, so nothing new to distribute. The two repos are kept apart by zot push rights, not keys. tap-agents' CI user can't push `tap/platform-manifests` or the service images. |
| Registry | A new zot user `tap-platform-ci` with read/create/update on `tap/{console,hooks,egress-proxy,factory,factory-publisher}` and `tap/platform-manifests`, and no deletes. Its password goes in OpenBao `secret/tap-platform-ci/zot`. | It's separate from `tap-ci` in both directions: tap-agents can't push platform images, and this repo can't push agents. |
| CI network | The same Tailscale workload identity federation as tap-agents (`tag:tap-ci`), with a federated credential for this repo | CI needs zot (`:443`) and OpenBao (`:8443`). It doesn't need the Kubernetes API, except to post the `tap/deploy` status (see phase 4). |

## What blocks Flux today

| Today | Must become |
| --- | --- |
| Digests are pinned in `deploy/platform/*.yaml` and `deploy/factory/factory.yaml` by `task image:push` | Plain image names in git, with digests set in the artifact |
| Infra and apps are mixed in one file per service (`console.yaml` holds the ClusterRole, Deployment and HTTPRoute) | `deploy/platform/{infra,apps}` and `deploy/factory/{infra,apps}` |
| `tap-platform` is applied separately by `task console:config` | A `configMapGenerator` in the apps kustomization |
| `platform:up` creates `egress-keys`, `egress-policy`, `agent-settings`, `agent-hooks` and `hooks-trigger-token` if they're missing | Unchanged and outside Flux: the console and ESO write them at runtime, and Flux must never prune or overwrite them |
| `egressProxy.image` in `platform.yaml` is pinned but nothing renders it | Removed, so the proxy's digest lives only in the artifact |

## Phases

### Phase 1: Split the manifests (in this repo)
- [x] Each service's Deployment and Service, and the NetworkPolicies that select only its own pods, are in `deploy/platform/apps/` and `deploy/factory/apps/`. Everything else is in `infra/`. `platform:up` and `factory:deploy` apply `infra/` only. **Changed from the plan:** `default-deny` in `tap-factory` and `tap-factory-to-inference` (in `envoy-gateway-system`) stay in `infra/`. One is a namespace-wide baseline, and the other is outside the namespaces the applier will get.
- [x] `apps/kustomization.yaml`: `configMapGenerator` for `tap-platform` from `../../../platform.yaml`, so builds need `--load-restrictor LoadRestrictionsNone`. **Changed from the plan:** no `images:` block in git. `deploy/apps.sh render` writes an overlay over both `apps/` directories with each image's digest, and CI will use the same script.
- [x] **Input tags, brought forward from phase 2.** `deploy/apps.sh tag <image>` was first the last commit that touched the image's inputs, and is now a hash of their contents (see phase 4's findings). The inputs are the module packages its binaries import (`go list -deps`), `go.mod`, `go.sum`, `images/<image>` and, for the factory, `factory/`. `images:push` pushes the five images under that tag and skips one that's already pushed. A rebuild would give the same tag a new digest.
- [x] `task platform:apps`: renders the apps layer at the input tags' digests (`crane digest`), applies it and waits for the rollouts. It also deletes the old unsuffixed `tap-platform`. Once Flux applies the layer, this is the break-glass path, and Flux reverts it on the next reconcile. `console:config` is gone.
- [x] `egressProxy.image` is gone from `platform.yaml`, `spec.PinImage` and `images:push`. `images:sign` signs the apps layer through `deploy/apps.sh refs`. **Changed from the plan:** the field stays in `spec.Platform`, unread. The factory's tapctl is built from `main` but validates against the `platform.yaml` of tap-agents' pinned release, which still has the field, and decoding is strict.
- [x] **Done (Oct 16, #54):** after `images:push` and `task platform:up && task platform:apps`, `kubectl diff` against both infra layers and `deploy/apps.sh render` is empty. All five services run their input tags' digests, all signed with `tap-build`, and the console reads `tap-platform-<hash>`. The unsuffixed `tap-platform` is gone.

Findings:
- **#52's reload fallback no longer fires in normal operation.** With a hash suffix, a `platform.yaml` change is a new ConfigMap and a new pod, and the mounted file never changes under a running console. What protects the console now is the rollout. A pod that can't load its `platform.yaml` exits, never becomes ready and leaves the old pod serving.

### Phase 2: CI builds and signs the images
- [x] OpenBao role `tap-platform-ci` (`deploy/openbao/onboard-platform-ci.sh`, `task ci:onboard:platform`): policies `tap-signer` and `tap-platform-ci`, which may read `secret/tap-platform-ci/*` only. It's bound to `repository=ipedrazas/tap`, `ref=refs/heads/main` and `job_workflow_ref` (`platform.yml` on main). **Changed from the plan:** a separate script and task, not more roles in `onboard-ci.sh`, so onboarding one repo's CI never rewrites the other's. `run.sh` has a `--policies` flag for it, which mounts no token.
- [x] zot user `tap-platform-ci` (`task registry:creds`, password in `.tap/registry-platform-ci.pass` and OpenBao). It may read, create and update `tap/{console,hooks,egress-proxy,factory,factory-publisher,platform-manifests}`, listed one by one, and it can't delete.
- [x] Tailscale trust credential for this repo (its own, not shared with tap-agents), subject `repo:ipedrazas@32796/tap@1410482453:ref:refs/heads/main`, tag `tag:tap-ci`; repository variables `TS_CLIENT_ID` and `TS_AUDIENCE`.
- [x] `.github/workflows/platform.yml`, on push to `main`, one run at a time:
  1. `checks`: calls `ci.yml` (`workflow_call`). ci.yml's concurrency group is now `${{ github.workflow }}-${{ github.ref }}`, so the called run and ci's own run on the same push don't cancel each other.
  2. `build` (matrix of the five images): `ci/build-image.sh`. It computes the input tag, builds with buildx only if zot doesn't have the tag, and signs the digest with `tap-build` unless it's signed already. The job summary lists tag, built or not, and digest.
- [x] **Done when:** a merge that touches only `cmd/console` builds and signs one image; a docs-only merge builds none.
  - [x] Builds none (Oct 16, #56, run 38901546171): all five input tags were already in zot, so each job only confirmed the signature. The tags and digests match what `task platform:apps` deployed.
  - [x] Builds one (Oct 16, #61, run 38930531388): only the console was built, under new tag `68414202d0e2`; the other four were already in zot.

### Phase 3: CI publishes the platform artifact
- [x] `publish` job (after `build`), running `ci/publish.sh`:
  - checks that every image at its input tag verifies against `tap-build`;
  - renders the apps layer (`deploy/apps.sh render`) and fails if any `image:` lacks a digest;
  - pushes it with `flux push artifact` to `tap/platform-manifests:<sha>` (`--revision main@sha1:<sha>`), signs it with `tap-build` and tags it `main`.
- [x] **Done (Oct 16, #57, run 38902234750):** `tap/platform-manifests:main` and `:<merge sha>` are the same digest. It verifies against `tap-build`, carries `main@sha1:<sha>` as its revision, and `kubectl diff` against its `apps.yaml` is empty. **Changed from the plan:** the plan expected only the ConfigMap rename, but phase 1 already applied that.

### Phase 4: Flux applies
- [x] `deploy/flux/platform.yaml`: `OCIRepository platform` (`tap/platform-manifests:main`, cosign against `tap-build-pub`) and `Kustomization platform` (`prune`, `wait`, 5-minute timeout, `serviceAccountName: tap-platform-applier`). `task flux:platform` applies them, and `flux:install` calls it.
- [x] `tap-platform-applier`: Roles in `tap-system` and `tap-factory` for deployments, services, configmaps and networkpolicies, plus read on replicasets for `wait`. No ClusterRole, Secrets, RBAC or exec. ConfigMaps can't be limited by name, so the applier could write any ConfigMap in those two namespaces, `agent-settings` included. It only ever applies what the signed artifact holds.
- [x] `deploy` job (15-minute timeout): posts `tap/deploy` (pending, then success or failure) and waits until the Kustomization's `lastAppliedOriginRevision` is this commit and it's Ready (`ci/wait-flux.sh`). **Changed from the plan:** it doesn't ask the source to fetch now. That needs `patch` on the OCIRepository, which RBAC can't limit to the reconcile annotation, so a CI token could also change the source's URL, tag or `verify`. The source polls every minute, so the cost is at most a minute. tap-agents' `tap-ci-runner` had the same `patch` on the `agents` source; tap-agents#14 and tap#64 dropped it.
  - **Changed from the plan:** the token is for `flux-system/tap-platform-ci-runner` (`deploy/ci/platform-rbac.yaml`), minted by OpenBao role `tap-kubernetes/roles/tap-platform-ci-runner` as the existing `openbao-ci-issuer`. It may only get and watch the `platform` Kustomization.
  - `ci:onboard:platform` now also writes that role and `secret/tap-platform-ci/kube`, so it runs with `run.sh --ci` and the `--policies` flag is gone.
- [x] `platform:apps` refuses when Flux manages the apps layer (`FORCE=1` overrides until the next reconcile). `factory:deploy` applies only the infra layer and secrets. `images:push` still pushes the apps images under their input tags, which CI then skips.
- [x] **Commits CI rejects get a red `tap/deploy`.** The `not-deployed` job posts a failure status when `checks`, `build` or `publish` fail; `deploy` reports its own result. Before this, a commit that failed early had no `tap/deploy` status at all.
- **Trust roots.** Flux verifies the artifact, not its own objects. Whoever can apply `deploy/flux/platform.yaml` (the operator, with `task flux:platform`) can point the source elsewhere or drop `verify`, as for the agents. Neither CI account can: `tap-platform-applier` has no rights in `flux-system`, and `tap-platform-ci-runner` can only read the Kustomization.
- [x] **Done (Oct 16):**
  - [x] a console change merged to `main` is live with no manual step. #60 rebuilt all five images under content tags, and Flux rolled every service onto them with `tap/deploy` green (run 38926307765). Before that, #58's `platform.yaml` change rolled the console onto `tap-platform-kkk5cdd976` and pruned the old ConfigMap;
  - [x] a console that can't start leaves the old pod serving and `tap/deploy` red. #61 made the console exit at startup (run 38930531388). The new pod crash-looped, and the old pod, `tap-console-846469b79-nt2wf`, was the Service's only ready endpoint throughout. The Kustomization's health check failed at its 5-minute timeout, and `tap/deploy` went red when the deploy job's wait ran out. This was first written as "a `platform.yaml` the running console can't parse", but CI stops that case (see findings);
  - [x] reverting rolls back without a rebuild. #62 reverted #61 (run 38932684853). The console's tag went back to `da306afe78d3`, already in zot, so nothing was built. Flux restored `sha256:f49ab478…`, the old ReplicaSet took over again, the old pod never restarted, and `tap/deploy` went green;
  - [x] editing a Deployment by hand is reverted on the next reconcile. On Oct 16, `tap-hooks` scaled to 2 at 15:03 UTC was back to 1 at 15:09, on the reconcile due 10 minutes after the previous one at 14:58. The original pod kept running.

Findings:
- **Commit-based input tags made reverts rebuild.** A revert is a new commit that touches the image's inputs, so it got a new tag and a rebuild: the same source, but a new digest. Tags are now a hash of the inputs' contents at HEAD, so identical sources always give the same tag, and a revert finds the old image in zot. It also works in a shallow clone. The merge that switched schemes rebuilt all five images once, under their new tags.
- **A `platform.yaml` the console can't parse never reaches Flux.** Decoding is strict, so CI's `go test` (the golden render tests load the repo's `platform.yaml`) and `tapctl` both reject an unknown field, and the run stops at `checks`. Input tags cover `pkg/spec` too, so the console is always rebuilt with the `platform.yaml` it ships with. The original Oct 16 skew can't recur. The rollout safety net is tested with a console that exits at startup instead.
