# tap: platform GitOps plan

Merging a change to a platform service should be enough to deploy it, as it already is for agents ([gitops-plan.md](gitops-plan.md)). Today someone runs `task images:push`, commits the new digests and runs `kubectl apply` by hand. Nothing ties the code that's running to the config it reads. On Oct 16 `task console:config` published a `platform.yaml` with `secrets.egressPrefix`, but the console running on the cluster was built before that field existed. It couldn't parse the file, so every agent's settings went read-only (#51, #52).

This plan builds the platform images in GitHub Actions and lets Flux apply them, together with `platform.yaml`, from one signed artifact per commit.

## Goals and non-goals

- **Merge = deploy** for the services that change often: console, hooks, egress-proxy, factory and factory-publisher.
- **Code and config ship together.** The `tap-platform` ConfigMap and the images that read it come from the same commit and the same artifact.
- **A bad config doesn't replace a good pod.** If a new build can't start with its config, the rollout stalls and the old pod keeps serving.
- **Revert = rollback**, as for agents.
- Not in scope: the infrastructure the services sit on. That's the gateway, certificate, zot, Dex, OpenBao objects, RBAC and the Secrets the console writes, and they keep `task platform:up` (see Decisions). Runner, harness and casa-collector images also stay out. They're pinned in `platform.yaml` and reach agents through tap releases (`tap.version`), which is a separate contract.

## Decisions (proposed)

| Topic | Proposal | Why |
| --- | --- | --- |
| What Flux owns | An **apps** layer: the services' Deployments, Services, NetworkPolicies and the `tap-platform` ConfigMap. The **infra** layer (Namespaces, RBAC, ServiceAccounts, HTTPRoutes, Gateway, Certificate, zot, PVCs, ESO objects, Secrets) stays with `task platform:up` and `task factory:deploy`. | Infra changes a few times a month, and applying it needs near-cluster-admin rights: whoever can create ClusterRoleBindings can grant themselves anything. The apps layer needs only namespaced Deployments, Services, ConfigMaps and NetworkPolicies, so its applier can be narrower than `tap-agents-applier`. zot also serves registry.hiddenfield.dev through the gateway, and Flux pulls the artifact from it. If Flux managed zot or the gateway, a bad rollout could cut off the source needed to fix it. |
| Trigger | Every push to `main` of this repo, after `ci.yml`'s checks pass | Same as agents. There's one cluster, so tags would only add a manual step back. |
| Digests | No digests in git. CI writes them into the artifact's `kustomization.yaml` (`kustomize edit set image`) | Without this, CI has to commit pins back to `main`, which means bot commits, CI loops and fights with branch protection. The artifact (`tap/platform-manifests:<sha>`) is the pinned record, and git history is still the source of truth. |
| What CI rebuilds | Each image is tagged with the last commit that touched its inputs (`git log -1 --format=%h -- <inputs>`). If zot already has that tag, the image isn't rebuilt. | A docs-only merge shouldn't restart every service. Docker builds aren't byte-reproducible, so we can't use the digest for change detection as we do for agents. This tag gives the same effect. |
| Config rollout | `tap-platform` is generated by `configMapGenerator` from `platform.yaml`, with the hash suffix kept | A `platform.yaml` change renames the ConfigMap, which rolls the Deployments that mount it. A console that can't load it exits at startup (`main.go`), so the new pod never becomes ready, the old one keeps serving and Flux's `wait` fails. #52's reload fallback stays as a second safety net. `task console:config` goes away. |
| Signing | The existing `tap-build` key (Transit `tap-signer`), through a new OpenBao JWT role `tap-platform-ci` bound to `ipedrazas/tap`, `refs/heads/main` and the platform workflow | `tap-build-pub` already sits in `flux-system`, so nothing new to distribute. The two repos are kept apart by zot push rights, not keys. tap-agents' CI user can't push `tap/platform-manifests` or the service images. |
| Registry | A new zot user `tap-platform-ci` with read/create/update on `tap/{console,hooks,egress-proxy,factory,factory-publisher}` and `tap/platform-manifests`, and no deletes. Its password goes in OpenBao `secret/tap-platform-ci/zot`. | It's separate from `tap-ci` in both directions: tap-agents can't push platform images, and this repo can't push agents. |
| CI network | The same Tailscale workload identity federation as tap-agents (`tag:tap-ci`), with a federated credential for this repo | CI needs zot (`:443`) and OpenBao (`:8443`). It doesn't need the Kubernetes API, except to post the `tap/deploy` status (see phase 4). |

## What blocks Flux today

| Today | Must become |
| --- | --- |
| Digests are pinned in `deploy/platform/*.yaml` and `deploy/factory/factory.yaml` by `task image:push` | Plain image names in git, with digests set in the artifact |
| Infra and apps are mixed in one file per service (`console.yaml` holds the ClusterRole, Deployment and HTTPRoute) | `deploy/platform/{infra,apps}` and `deploy/factory/{infra,apps}` |
| `tap-platform` is applied separately by `task console:config` | A `configMapGenerator` in the apps kustomization |
| `platform:up` creates `egress-keys`, `egress-policy`, `agent-settings`, `agent-hooks` and `hooks-trigger-token` if they're missing | Unchanged and outside Flux: the console and ESO write them at runtime, and Flux must never prune or overwrite them |
| `egressProxy.image` in `platform.yaml` is pinned but nothing renders it | Removed, so the proxy's digest lives only in the artifact |

## Phases

### Phase 1: Split the manifests (in this repo)
- [x] Each service's Deployment and Service, and the NetworkPolicies that select only its own pods, are in `deploy/platform/apps/` and `deploy/factory/apps/`. Everything else is in `infra/`. `platform:up` and `factory:deploy` apply `infra/` only. **Changed from the plan:** `default-deny` in `tap-factory` and `tap-factory-to-inference` (in `envoy-gateway-system`) stay in `infra/`. One is a namespace-wide baseline, and the other is outside the namespaces the applier will get.
- [x] `apps/kustomization.yaml`: `configMapGenerator` for `tap-platform` from `../../../platform.yaml`, so builds need `--load-restrictor LoadRestrictionsNone`. **Changed from the plan:** no `images:` block in git. `deploy/apps.sh render` writes an overlay over both `apps/` directories with each image's digest, and CI will use the same script.
- [x] **Input tags, brought forward from phase 2.** `deploy/apps.sh tag <image>` is the first 12 characters of the last commit that touched the image's inputs: the module packages its binaries import (`go list -deps`), `go.mod`, `go.sum`, `images/<image>` and, for the factory, `factory/`. `images:push` pushes the five images under that tag and skips one that's already pushed. A rebuild would give the same tag a new digest.
- [x] `task platform:apps`: renders the apps layer at the input tags' digests (`crane digest`), applies it and waits for the rollouts. It also deletes the old unsuffixed `tap-platform`. Once Flux applies the layer, this is the break-glass path, and Flux reverts it on the next reconcile. `console:config` is gone.
- [x] `egressProxy.image` is gone from `platform.yaml`, `spec.PinImage` and `images:push`. `images:sign` signs the apps layer through `deploy/apps.sh refs`. **Changed from the plan:** the field stays in `spec.Platform`, unread. The factory's tapctl is built from `main` but validates against the `platform.yaml` of tap-agents' pinned release, which still has the field, and decoding is strict.
- [ ] **Done when:** `task platform:up && task platform:apps` from a clean checkout gives the same live objects as today, apart from the ConfigMap name.

Findings:
- **#52's reload fallback no longer fires in normal operation.** With a hash suffix, a `platform.yaml` change is a new ConfigMap and a new pod, and the mounted file never changes under a running console. What protects the console now is the rollout. A pod that can't load its `platform.yaml` exits, never becomes ready and leaves the old pod serving.

### Phase 2: CI builds and signs the images
- [ ] OpenBao role `tap-platform-ci` (`deploy/openbao/onboard-ci.sh`): `tap-signer` plus read on `secret/tap-platform-ci/zot`, bound to `repository=ipedrazas/tap`, `ref=refs/heads/main` and `job_workflow_ref` (the platform workflow).
- [ ] zot user `tap-platform-ci`, as above.
- [ ] Tailscale federated credential for this repo. Bind it on `repository`, not `sub`: the `sub` claim uses immutable IDs (see the gitops plan's phase 4 findings).
- [ ] `.github/workflows/platform.yml`, on push to `main`:
  1. `checks`: calls `ci.yml` (`workflow_call`), so nothing is built from a commit that fails tests.
  2. `build` (matrix of the five images): `deploy/apps.sh tag`, skip if zot has it, otherwise `docker buildx` for linux/amd64, push and sign with `tap-build`. The checkout needs full history (`fetch-depth: 0`), or `git log` can't find the input commit.
- **Done when:** a merge that touches only `cmd/console` builds and signs one image; a docs-only merge builds none.

### Phase 3: CI publishes the platform artifact
- [ ] `publish` job: `deploy/apps.sh render`. Check that every image is signed, then `flux push artifact` to `tap/platform-manifests:<sha>`, sign it with `tap-build` and tag it `main`.
- **Done when:** `tap/platform-manifests:main` verifies with `cosign verify --key tap-build.pub` and `kubectl diff` against it shows only the ConfigMap rename.

### Phase 4: Flux applies
- [ ] `deploy/flux/platform.yaml`: `OCIRepository platform` (`tap/platform-manifests:main`, cosign against `tap-build-pub`) and `Kustomization platform` (`prune`, `wait`, 5-minute timeout, `serviceAccountName: tap-platform-applier`).
- [ ] `tap-platform-applier`: namespaced Roles in `tap-system` and `tap-factory` for deployments, services, configmaps and networkpolicies, plus read on replicasets for `wait`. No ClusterRole, and no Secrets, RBAC or exec.
- [ ] `deploy` job: posts the `tap/deploy` commit status the way tap-agents does, which needs a `tap-platform-ci-runner` that can read the Kustomization and annotate the source in `flux-system`.
- [ ] `images:push` keeps only runners, harness and casa-collector. `factory:deploy` and `platform:up` stop applying the apps layer.
- **Done when:**
  - a console change merged to `main` is live with no manual step;
  - a `platform.yaml` the running console can't parse leaves the old pod serving and `tap/deploy` red;
  - reverting rolls back without a rebuild (the input tag is still in zot);
  - editing a Deployment by hand is reverted on the next reconcile.

### Later
- [ ] Alerts on failed reconciles to a console banner (shared with the agents plan, phase 5).
- [ ] The infra layer under Flux, as a second Kustomization with its own, wider applier, if it starts changing often enough to be worth it.
- [ ] Build runner and harness images on `v*` tags in `release.yml`, so the `platform.yaml` that tap-agents pins always names images CI built.
